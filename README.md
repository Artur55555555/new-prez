# Конспект: Тестирование программного обеспечения

## 1. Что такое тестирование и зачем оно нужно
**Тестирование ПО** — это процесс проверки соответствия программы требованиям и выявления дефектов (ошибок) до того, как их обнаружит пользователь.

**Цели тестирования:**
*   Убедиться, что программа делает то, что должна (соответствие ТЗ).
*   Найти ошибки и баги на ранних этапах (дешевле исправлять).
*   Проверить стабильность и производительность.
*   Обеспечить безопасность и удобство для пользователя (UX).

## 2. Уровни тестирования (Пирамида тестирования)
Тестирование делится на уровни, от самых мелких частей кода до всей системы целиком.

1.  **Модульное (Unit) тестирование** — проверка отдельных функций, методов или классов. Самый быстрый и дешёвый уровень. Пишется самими разработчиками.
2.  **Интеграционное тестирование** — проверка взаимодействия между модулями (например, как база данных работает с логикой приложения).
3.  **Системное тестирование** — проверка всей системы целиком, как единого организма (включая UI, API, БД).
4.  **Приёмочное (Acceptance) тестирование** — проверка соответствия бизнес-требованиям. Обычно проводится заказчиком или конечным пользователем перед релизом.

## 3. Виды тестирования (по доступу к коду)
*   **Белое ящик (White Box)** — тестировщик знает внутреннее устройство кода. Проверяется логика ветвлений, циклы, покрытие кода (Code Coverage).
*   **Чёрный ящик (Black Box)** — тестировщик не знает, как устроен код. Он проверяет только входные данные и результат (например, нажатие кнопки -> реакция интерфейса).
*   **Серый ящик (Grey Box)** — комбинация: есть доступ к коду, но проверка идёт через интерфейс или API.

## 4. Виды тестирования (по функциональности)
*   **Функциональное** — проверка того, что программа работает (кнопки нажимаются, данные сохраняются). Основной вид.
*   **Регрессионное** — повторная проверка старого функционала после внесения изменений (чтобы новое не сломало старое).
*   **Smoke (Дымовое)** — быстрая проверка основной работоспособности после сборки (запускается ли программа вообще, открывается ли главное окно).
*   **Нагрузочное** — проверка работы системы при высокой нагрузке (много пользователей одновременно).
*   **Юзабилити** — проверка удобства интерфейса для пользователя.
*   **Безопасность** — проверка на уязвимости (SQL-инъекции, XSS и т.д.).

## 5. Ключевые техники тест-дизайна
Чтобы не тестировать всё подряд, используют специальные техники:
1.  **Классы эквивалентности** — разбиение входных данных на группы, которые обрабатываются одинаково (например, если вводить число от 1 до 10, то тестировать 3 и 7 не имеет смысла, достаточно одного значения из группы).
2.  **Граничные значения** — проверка значений на границах диапазона (например, для диапазона 1-10 проверяем 0, 1, 10, 11).
3.  **Попарное тестирование (Pairwise)** — проверка комбинаций параметров (когда входных параметров много, проверяются не все комбинации, а только самые вероятные).

## 6. Жизненный цикл бага (Bug Life Cycle)
Когда тестировщик находит ошибку, она проходит путь:
1.  **New** (Новый) — баг найден и задокументирован.
2.  **Assigned** (Назначен) — передан разработчику.
3.  **Open** (Открыт) — разработчик начал работу.
4.  **Fixed** (Исправлен) — разработчик внёс правки.
5.  **Retest** (Проверка) — тестировщик проверяет, исчезла ли ошибка.
6.  **Closed** (Закрыт) — баг исправлен и подтверждён.

## 7. Инструменты тестирования
*   **Для юнит-тестов (C#):** NUnit, xUnit, MSTest.
*   **Для UI (автоматизация):** Selenium (для веба), Appium (для мобильных), WinAppDriver (для Windows).
*   **Для API:** Postman, SoapUI.
*   **Для баг-трекинга:** Jira, Azure DevOps, Redmine.
*   **Для нагрузочного:** JMeter, LoadRunner.

## 8. Важные термины
*   **Тест-кейс (Test Case)** — документ, описывающий шаги, входные данные и ожидаемый результат для проверки.
*   **Тест-сьют (Test Suite)** — набор тест-кейсов.
*   **Баг (Bug/Defect)** — несоответствие фактического поведения программы ожидаемому.
*   **Покрытие кода (Code Coverage)** — процент кода, который был выполнен во время тестов (чем выше, тем лучше, но 100% не гарантирует отсутствие багов).
*   **Регресс** — ошибка, которая появилась из-за того, что новое изменение сломало старый код.

## 9. Принципы тестирования (по ISTQB)
1.  Тестирование демонстрирует наличие дефектов, а не их отсутствие.
2.  Исчерпывающее тестирование невозможно (нельзя перебрать все варианты).
3.  Раннее тестирование экономит время и деньги.
4.  Тестирование зависит от контекста (банковское ПО тестируется иначе, чем игра).
5.  Парадокс пестицида: если гонять одни и те же тесты, они перестают находить новые баги (нужно обновлять тесты).

# Конспект: UML-диаграммы 

## 1. Что такое UML и зачем он нужен
**UML (Unified Modeling Language)** — это унифицированный язык моделирования. Это **не язык программирования**, а графическая нотация (набор стандартов), которая позволяет визуализировать, специфицировать и документировать архитектуру программных систем.

**Зачем нужен UML:**
*   **Общение:** единый язык для разработчиков, аналитиков и заказчиков (все понимают схему одинаково).
*   **Проектирование:** позволяет продумать структуру до написания кода.
*   **Документация:** диаграммы служат технической документацией проекта.
*   **Анализ:** помогает увидеть узкие места и ошибки в архитектуре.

## 2. Классификация диаграмм UML
Все диаграммы делятся на две большие группы:

1.  **Структурные (Structural)** — показывают *что* состоит из чего (статическая структура системы).
2.  **Поведенческие (Behavioral)** — показывают *как* система работает (динамика, взаимодействие).

## 3. Основные виды диаграмм (Топ-5 для практики)

### 3.1. Диаграмма классов (Class Diagram) — Структурная
Самая популярная диаграмма. Показывает классы, их атрибуты, методы и связи между ними.

*   **Класс** изображается прямоугольником с тремя секциями:
    *   Имя класса.
    *   Атрибуты (поля/свойства).
    *   Методы (операции).
*   **Связи (Отношения):**
    *   **Ассоциация** (простая линия) — «один использует другого».
    *   **Агрегация** (ромб без заливки) — «содержит, но часть может существовать отдельно» (например, Автомобиль и Колесо).
    *   **Композиция** (ромб с заливкой) — «жесткая связь» (часть не может существовать без целого, например, Дом и Этаж).
    *   **Наследование** (стрелка с пустым треугольником) — «является» (например, Собака наследует Животное).
    *   **Реализация** (пунктирная линия со стрелкой) — класс реализует интерфейс.
*   **Мощность (кратность):** `1`, `0..1`, `*` (много), `1..*` (один и более).

### 3.2. Диаграмма вариантов использования (Use Case Diagram) — Поведенческая
Показывает, *что* система должна делать с точки зрения пользователя.

*   **Актор** (человечек) — пользователь или внешняя система.
*   **Прецедент/Вариант использования** (овал) — действие, которое выполняет актор (например, «Купить товар»).
*   **Связи:** ассоциации (актор-прецедент), `include` (обязательное включение), `extend` (опциональное расширение).
*   **Системная граница** (прямоугольник) — рамка, ограничивающая систему.

### 3.3. Диаграмма последовательности (Sequence Diagram) — Поведенческая
Показывает обмен сообщениями между объектами во времени.

*   **Вертикальная ось** — время (сверху вниз).
*   **Объекты** (прямоугольники сверху) — участники взаимодействия.
*   **Линия жизни** (пунктир вниз) — существование объекта во времени.
*   **Сообщения** (стрелки) — вызовы методов или передача данных.
*   **Активация** (узкий прямоугольник на линии жизни) — период, когда объект что-то выполняет.
*   *Используется для проектирования взаимодействия (например, «Пользователь нажимает кнопку -> Контроллер вызывает БД -> БД возвращает данные»).*

### 3.4. Диаграмма активностей (Activity Diagram) — Поведенческая
Аналог блок-схемы. Показывает поток управления или поток данных.

*   **Начало** (закрашенный круг) и **Конец** (круг с точкой).
*   **Действия** (прямоугольники с закруглёнными углами) — шаги алгоритма.
*   **Ромбы** — решения (ветвления).
*   **Параллельные ветки** (жирная горизонтальная линия) — fork/join (разделение и слияние потоков).

### 3.5. Диаграмма состояний (State Machine Diagram) — Поведенческая
Показывает, как меняется состояние объекта в ответ на события.

*   **Состояния** (прямоугольники с закруглёнными углами) — например, «Ожидание», «В обработке», «Завершено».
*   **Переходы** (стрелки) — переход из одного состояния в другое по триггеру (событию).
*   *Используется для объектов со сложным жизненным циклом (например, Заказ: Новый -> Оплачен -> Отправлен -> Доставлен).*

## 4. Связи в UML (Кратко)
*   **Зависимость** (пунктирная стрелка) — слабая связь, изменение одного влияет на другого.
*   **Ассоциация** (линия) — объекты знают друг о друге.
*   **Обобщение** (стрелка с треугольником) — наследование.
*   **Реализация** (пунктир с треугольником) — реализация интерфейса.

## 5. Инструменты для создания UML
*   **Visual Studio** (встроенный конструктор классов и диаграмм).
*   **PlantUML** — создание диаграмм через код (текстом).
*   **draw.io / diagrams.net** — бесплатный онлайн-редактор.
*   **Lucidchart** — профессиональный веб-инструмент.
*   **StarUML** — десктопная программа.

## 6. Принципы хорошей UML-диаграммы
1.  **Не перегружайте:** не показывайте все классы проекта, только ключевые.
2.  **Соблюдайте нотацию:** используйте правильные стрелки и ромбы.
3.  **Уровень детализации:** диаграмма должна быть понятна целевой аудитории (для бизнеса — Use Case, для разработчиков — Class).
4.  **Именование:** имена классов и методов должны быть понятными (не `Class1`, `Method2`).

## 7. Пример: Как связаны диаграммы в проекте
1.  **Use Case** — определяем, *что* нужно пользователю.
2.  **Class Diagram** — проектируем *структуру* кода (какие классы создадим).
3.  **Sequence Diagram** — продумываем *логику* взаимодействия (как методы вызывают друг друга).
4.  **State Diagram** — описываем *поведение* сложных объектов (например, статус заказа).
