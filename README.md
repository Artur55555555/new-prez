# 1. Что такое разработка ПО

**Разработка программного обеспечения** — это процесс создания, тестирования, внедрения и сопровождения программ.

Обычно разработка включает несколько этапов:

```text
Идея
  ↓
Анализ требований
  ↓
Проектирование
  ↓
Написание кода
  ↓
Тестирование
  ↓
Релиз
  ↓
Поддержка и улучшение
```

Главная задача разработчика — не просто написать код, который работает, а создать систему, которую будет удобно:

* понимать;
* изменять;
* тестировать;
* расширять;
* исправлять;
* поддерживать.

# 2. Основные принципы разработки

Существует множество принципов программирования. Некоторые из самых известных:

| Принцип                        | Основная идея                                                  |
| ------------------------------ | -------------------------------------------------------------- |
| **KISS**                       | Делай решение максимально простым                              |
| **DRY**                        | Не повторяй один и тот же код                                  |
| **YAGNI**                      | Не реализуй то, что сейчас не требуется                        |
| **SRP**                        | Один компонент — одна ответственность                          |
| **OCP**                        | Код должен быть открыт для расширения, но закрыт для изменения |
| **Разделение ответственности** | Разные части системы должны выполнять разные задачи            |
| **Композиция**                 | Сложное поведение лучше собирать из небольших компонентов      |

---

## 2.1 KISS

**KISS — Keep It Simple, Stupid.**

Смысл принципа: **если задачу можно решить простым способом, не нужно усложнять решение.**

### Плохо

```python
def is_adult(age):
    if age >= 18:
        return True
    else:
        return False
```

### Лучше

```python
def is_adult(age):
    return age >= 18
```

Второй вариант короче и сразу показывает смысл функции.

### Главное

> Простое решение обычно легче понять, протестировать и изменить.

---

## 2.2 DRY

**DRY — Don't Repeat Yourself.**

Не следует многократно копировать одинаковую логику.

### Плохо

```python
price1 = price1 * 0.9
price2 = price2 * 0.9
price3 = price3 * 0.9
```

### Лучше

```python
def apply_discount(price):
    return price * 0.9

price1 = apply_discount(price1)
price2 = apply_discount(price2)
price3 = apply_discount(price3)
```

Теперь если размер скидки изменится, достаточно изменить одну функцию.

### Однако

DRY не означает, что **любое повторение строк кода нужно немедленно выносить в функцию**.

Иногда небольшое дублирование делает код понятнее, чем слишком сложная абстракция.

---

## 2.3 YAGNI

**YAGNI — You Aren't Gonna Need It.**

Не нужно реализовывать функциональность заранее, если она пока не нужна.

### Например

Допустим, сейчас приложение поддерживает только пользователей из одной страны.

Не стоит заранее создавать сложную систему для:

* 50 стран;
* 20 валют;
* 15 языков;
* нескольких налоговых систем,

если требований на это пока нет.

### Идея

```text
Требуется сейчас → реализуем

Возможно понадобится когда-нибудь → пока не реализуем
```

Это позволяет уменьшить количество лишнего кода.

---

## 2.4 Разделение ответственности

Каждая часть программы должна заниматься своей задачей.

Например, приложение интернет-магазина может иметь:

```text
UserService
    ↓
Работа с пользователями

OrderService
    ↓
Работа с заказами

PaymentService
    ↓
Работа с платежами

EmailService
    ↓
Отправка писем
```

Не стоит помещать всю бизнес-логику приложения в один огромный класс или файл.

---

## 2.5 Принцип единственной ответственности (SRP)

**SRP — Single Responsibility Principle.**

Класс или функция должны иметь **одну основную ответственность**.

### Плохой пример

```python
class User:
    def save_to_database(self):
        pass

    def send_email(self):
        pass

    def generate_report(self):
        pass
```

Класс `User` занимается сразу несколькими задачами.

### Более подходящий вариант

```python
class User:
    pass


class UserRepository:
    def save(self, user):
        pass


class EmailService:
    def send(self, user):
        pass


class ReportService:
    def generate(self, user):
        pass
```

Теперь ответственность разделена.

---

## 2.6 Принцип открытости/закрытости (OCP)

**OCP — Open/Closed Principle.**

Программные компоненты должны быть:

* **открыты для расширения**;
* **закрыты для изменения существующей логики**.

Например, вместо большого `if`:

```python
if payment_type == "card":
    ...
elif payment_type == "paypal":
    ...
elif payment_type == "crypto":
    ...
```

можно использовать отдельные реализации:

```python
class CardPayment:
    def pay(self, amount):
        pass


class PayPalPayment:
    def pay(self, amount):
        pass


class CryptoPayment:
    def pay(self, amount):
        pass
```

Тогда добавление нового способа оплаты не требует переписывать существующие классы.

---

## 2.7 Композиция вместо наследования

Иногда вместо создания сложной иерархии классов лучше объединять небольшие компоненты.

Например:

```text
Car
 ├── Engine
 ├── GPS
 └── AudioSystem
```

Автомобиль **содержит** двигатель, GPS и аудиосистему.

Такой подход называется **композицией**.

Он позволяет заменять отдельные компоненты независимо друг от друга.

# 3. Чистый код

**Clean Code** — код, который легко читать, понимать и изменять.

### Основные правила

* Использовать понятные названия.
* Делать функции небольшими.
* Не создавать огромные классы.
* Избегать ненужных комментариев.
* Не дублировать код.
* Соблюдать единый стиль.

### Плохое название

```python
x = 15
```

### Хорошее название

```python
user_age = 15
```

Название переменной должно объяснять её назначение.

---

## Пример

### Плохо

```python
def calc(a, b, c):
    x = a * b
    y = x - c
    return y
```

### Лучше

```python
def calculate_final_price(price, quantity, discount):
    total_price = price * quantity
    final_price = total_price - discount

    return final_price
```

Второй вариант длиннее, но его значительно легче понять.

# 4. Структура проекта

Хорошая структура проекта помогает быстро находить нужный код.

Например:

```text
project/
│
├── src/
│   ├── models/
│   ├── services/
│   ├── controllers/
│   └── utils/
│
├── tests/
│   ├── unit/
│   └── integration/
│
├── docs/
│
├── README.md
├── .gitignore
└── requirements.txt
```

### Возможное назначение каталогов

| Каталог        | Назначение              |
| -------------- | ----------------------- |
| `src/`         | Основной исходный код   |
| `models/`      | Модели данных           |
| `services/`    | Бизнес-логика           |
| `controllers/` | Обработка запросов      |
| `utils/`       | Вспомогательные функции |
| `tests/`       | Тесты                   |
| `docs/`        | Документация            |

Структура зависит от языка и типа проекта, поэтому не существует единственной правильной структуры для всех приложений.

# 5. Работа с Git

**Git** — система контроля версий.

Она позволяет:

* сохранять историю изменений;
* создавать ветки;
* работать нескольким разработчикам;
* возвращаться к предыдущим версиям;
* просматривать изменения.

### Основной workflow

```text
Изменение файлов
      ↓
git add
      ↓
git commit
      ↓
git push
      ↓
GitHub
```

### Пример

```bash
git add .
git commit -m "Add user authentication"
git push
```

### Хороший commit

```text
Add user authentication
```

### Плохой commit

```text
fix
```

или

```text
changes
```

Сообщение commit должно объяснять, что именно было изменено.

# 6. Тестирование

Тестирование помогает находить ошибки до того, как они попадут к пользователям.

Основные виды тестов:

| Тип                | Что проверяет                             |
| ------------------ | ----------------------------------------- |
| Unit-тест          | Отдельную функцию или небольшой компонент |
| Integration-тест   | Взаимодействие нескольких компонентов     |
| E2E-тест           | Работу системы целиком                    |
| Регрессионный тест | Что старый функционал не сломался         |

### Пример unit-теста

Допустим, есть функция:

```python
def add(a, b):
    return a + b
```

Тест:

```python
def test_add():
    assert add(2, 3) == 5
```

Тестирование особенно важно для критически важной бизнес-логики.

# 8. Обработка ошибок

Ошибки должны обрабатываться предсказуемо.

### Плохо

```python
try:
    result = calculate()
except:
    pass
````

Проблема: ошибка полностью скрывается.

### Лучше

```python
try:
    result = calculate()
except ValueError as error:
    print(f"Некорректное значение: {error}")
```

Важно:

* не скрывать ошибки без причины;
* использовать подходящий тип исключения;
* давать понятные сообщения;
* логировать важные ошибки;
* не показывать пользователю конфиденциальные данные.

# 9. Безопасность

Безопасность должна учитываться ещё во время разработки.

Основные правила:

* не хранить пароли в исходном коде;
* не хранить API-ключи в Git;
* проверять входные данные;
* использовать безопасные методы авторизации;
* обновлять зависимости;
* ограничивать права пользователей;
* не доверять данным от клиента.

### Плохо

```python
DATABASE_PASSWORD = "my-secret-password"
```

### Лучше

Использовать переменные окружения:

```python
import os

DATABASE_PASSWORD = os.getenv("DATABASE_PASSWORD")
```

И добавить секретные файлы в `.gitignore`.

# 10. Пример хорошего подхода

Представим задачу:

> Нужно создать функцию регистрации пользователя.

Не стоит сразу писать всё в одном месте.

### Плохой вариант

```python
def register_user(name, email, password):
    # проверка данных
    # хеширование пароля
    # работа с БД
    # отправка email
    # создание ответа
    ...
```

Функция выполняет слишком много задач.

### Более структурированный вариант

```text
RegistrationService
        │
        ├── Validator
        │
        ├── PasswordHasher
        │
        ├── UserRepository
        │
        └── EmailService
```

Каждый компонент отвечает за свою задачу.

### Преимущества

| Подход                 | Результат              |
| ---------------------- | ---------------------- |
| Большая функция        | Сложно тестировать     |
| Много обязанностей     | Сложно изменять        |
| Разделение компонентов | Проще тестировать      |
| Понятные названия      | Проще читать           |
| Небольшие функции      | Проще переиспользовать |

# 12. Заключение

Основные принципы разработки ПО помогают создавать программы, которые не только работают сегодня, но и остаются удобными для развития в будущем.

Самые важные идеи:

> **KISS** — не усложняй без необходимости.

> **DRY** — избегай ненужного дублирования.

> **YAGNI** — не реализуй функциональность заранее.

> **SRP** — разделяй ответственность.

> **Clean Code** — пиши код, который легко читать.

> **Тестирование** — проверяй работу программы автоматически.

> **Git** — сохраняй историю изменений.

> **Документация** — объясняй, как работает проект.

> **Безопасность** — учитывай её на всех этапах разработки.

# Конспект: Тестирование программного обеспечения

## 1. Что такое тестирование и зачем оно нужно
**Тестирование ПО** — это процесс проверки соответствия программы требованиям и выявления дефектов (ошибок) до того, как их обнаружит пользователь.

**Цели тестирования:**
*   Убедиться, что программа делает то, что должна (соответствие ТЗ).
*   Найти ошибки и баги на ранних этапах (дешевле исправлять).
*   Проверить стабильность и производительность.
*   Обеспечить безопасность и удобство для пользователя (UX).

## 2. Уровни тестирования (Пирамида тестирования)
Тестирование делится на уровни, от самых мелких частей кода до всей системы целиком.

1.  **Модульное (Unit) тестирование** — проверка отдельных функций, методов или классов. Самый быстрый и дешёвый уровень. Пишется самими разработчиками.
2.  **Интеграционное тестирование** — проверка взаимодействия между модулями (например, как база данных работает с логикой приложения).
3.  **Системное тестирование** — проверка всей системы целиком, как единого организма (включая UI, API, БД).
4.  **Приёмочное (Acceptance) тестирование** — проверка соответствия бизнес-требованиям. Обычно проводится заказчиком или конечным пользователем перед релизом.

## 3. Виды тестирования (по доступу к коду)
*   **Белое ящик (White Box)** — тестировщик знает внутреннее устройство кода. Проверяется логика ветвлений, циклы, покрытие кода (Code Coverage).
*   **Чёрный ящик (Black Box)** — тестировщик не знает, как устроен код. Он проверяет только входные данные и результат (например, нажатие кнопки -> реакция интерфейса).
*   **Серый ящик (Grey Box)** — комбинация: есть доступ к коду, но проверка идёт через интерфейс или API.

## 4. Виды тестирования (по функциональности)
*   **Функциональное** — проверка того, что программа работает (кнопки нажимаются, данные сохраняются). Основной вид.
*   **Регрессионное** — повторная проверка старого функционала после внесения изменений (чтобы новое не сломало старое).
*   **Smoke (Дымовое)** — быстрая проверка основной работоспособности после сборки (запускается ли программа вообще, открывается ли главное окно).
*   **Нагрузочное** — проверка работы системы при высокой нагрузке (много пользователей одновременно).
*   **Юзабилити** — проверка удобства интерфейса для пользователя.
*   **Безопасность** — проверка на уязвимости (SQL-инъекции, XSS и т.д.).

## 5. Ключевые техники тест-дизайна
Чтобы не тестировать всё подряд, используют специальные техники:
1.  **Классы эквивалентности** — разбиение входных данных на группы, которые обрабатываются одинаково (например, если вводить число от 1 до 10, то тестировать 3 и 7 не имеет смысла, достаточно одного значения из группы).
2.  **Граничные значения** — проверка значений на границах диапазона (например, для диапазона 1-10 проверяем 0, 1, 10, 11).
3.  **Попарное тестирование (Pairwise)** — проверка комбинаций параметров (когда входных параметров много, проверяются не все комбинации, а только самые вероятные).

## 6. Жизненный цикл бага (Bug Life Cycle)
Когда тестировщик находит ошибку, она проходит путь:
1.  **New** (Новый) — баг найден и задокументирован.
2.  **Assigned** (Назначен) — передан разработчику.
3.  **Open** (Открыт) — разработчик начал работу.
4.  **Fixed** (Исправлен) — разработчик внёс правки.
5.  **Retest** (Проверка) — тестировщик проверяет, исчезла ли ошибка.
6.  **Closed** (Закрыт) — баг исправлен и подтверждён.

## 7. Инструменты тестирования
*   **Для юнит-тестов (C#):** NUnit, xUnit, MSTest.
*   **Для UI (автоматизация):** Selenium (для веба), Appium (для мобильных), WinAppDriver (для Windows).
*   **Для API:** Postman, SoapUI.
*   **Для баг-трекинга:** Jira, Azure DevOps, Redmine.
*   **Для нагрузочного:** JMeter, LoadRunner.

## 8. Важные термины
*   **Тест-кейс (Test Case)** — документ, описывающий шаги, входные данные и ожидаемый результат для проверки.
*   **Тест-сьют (Test Suite)** — набор тест-кейсов.
*   **Баг (Bug/Defect)** — несоответствие фактического поведения программы ожидаемому.
*   **Покрытие кода (Code Coverage)** — процент кода, который был выполнен во время тестов (чем выше, тем лучше, но 100% не гарантирует отсутствие багов).
*   **Регресс** — ошибка, которая появилась из-за того, что новое изменение сломало старый код.

## 9. Принципы тестирования (по ISTQB)
1.  Тестирование демонстрирует наличие дефектов, а не их отсутствие.
2.  Исчерпывающее тестирование невозможно (нельзя перебрать все варианты).
3.  Раннее тестирование экономит время и деньги.
4.  Тестирование зависит от контекста (банковское ПО тестируется иначе, чем игра).
5.  Парадокс пестицида: если гонять одни и те же тесты, они перестают находить новые баги (нужно обновлять тесты).

# Конспект: UML-диаграммы 

## 1. Что такое UML и зачем он нужен
**UML (Unified Modeling Language)** — это унифицированный язык моделирования. Это **не язык программирования**, а графическая нотация (набор стандартов), которая позволяет визуализировать, специфицировать и документировать архитектуру программных систем.

**Зачем нужен UML:**
*   **Общение:** единый язык для разработчиков, аналитиков и заказчиков (все понимают схему одинаково).
*   **Проектирование:** позволяет продумать структуру до написания кода.
*   **Документация:** диаграммы служат технической документацией проекта.
*   **Анализ:** помогает увидеть узкие места и ошибки в архитектуре.

## 2. Классификация диаграмм UML
Все диаграммы делятся на две большие группы:

1.  **Структурные (Structural)** — показывают *что* состоит из чего (статическая структура системы).
2.  **Поведенческие (Behavioral)** — показывают *как* система работает (динамика, взаимодействие).

## 3. Основные виды диаграмм (Топ-5 для практики)

### 3.1. Диаграмма классов (Class Diagram) — Структурная
Самая популярная диаграмма. Показывает классы, их атрибуты, методы и связи между ними.

*   **Класс** изображается прямоугольником с тремя секциями:
    *   Имя класса.
    *   Атрибуты (поля/свойства).
    *   Методы (операции).
*   **Связи (Отношения):**
    *   **Ассоциация** (простая линия) — «один использует другого».
    *   **Агрегация** (ромб без заливки) — «содержит, но часть может существовать отдельно» (например, Автомобиль и Колесо).
    *   **Композиция** (ромб с заливкой) — «жесткая связь» (часть не может существовать без целого, например, Дом и Этаж).
    *   **Наследование** (стрелка с пустым треугольником) — «является» (например, Собака наследует Животное).
    *   **Реализация** (пунктирная линия со стрелкой) — класс реализует интерфейс.
*   **Мощность (кратность):** `1`, `0..1`, `*` (много), `1..*` (один и более).

### 3.2. Диаграмма вариантов использования (Use Case Diagram) — Поведенческая
Показывает, *что* система должна делать с точки зрения пользователя.

*   **Актор** (человечек) — пользователь или внешняя система.
*   **Прецедент/Вариант использования** (овал) — действие, которое выполняет актор (например, «Купить товар»).
*   **Связи:** ассоциации (актор-прецедент), `include` (обязательное включение), `extend` (опциональное расширение).
*   **Системная граница** (прямоугольник) — рамка, ограничивающая систему.

### 3.3. Диаграмма последовательности (Sequence Diagram) — Поведенческая
Показывает обмен сообщениями между объектами во времени.

*   **Вертикальная ось** — время (сверху вниз).
*   **Объекты** (прямоугольники сверху) — участники взаимодействия.
*   **Линия жизни** (пунктир вниз) — существование объекта во времени.
*   **Сообщения** (стрелки) — вызовы методов или передача данных.
*   **Активация** (узкий прямоугольник на линии жизни) — период, когда объект что-то выполняет.
*   *Используется для проектирования взаимодействия (например, «Пользователь нажимает кнопку -> Контроллер вызывает БД -> БД возвращает данные»).*

### 3.4. Диаграмма активностей (Activity Diagram) — Поведенческая
Аналог блок-схемы. Показывает поток управления или поток данных.

*   **Начало** (закрашенный круг) и **Конец** (круг с точкой).
*   **Действия** (прямоугольники с закруглёнными углами) — шаги алгоритма.
*   **Ромбы** — решения (ветвления).
*   **Параллельные ветки** (жирная горизонтальная линия) — fork/join (разделение и слияние потоков).

### 3.5. Диаграмма состояний (State Machine Diagram) — Поведенческая
Показывает, как меняется состояние объекта в ответ на события.

*   **Состояния** (прямоугольники с закруглёнными углами) — например, «Ожидание», «В обработке», «Завершено».
*   **Переходы** (стрелки) — переход из одного состояния в другое по триггеру (событию).
*   *Используется для объектов со сложным жизненным циклом (например, Заказ: Новый -> Оплачен -> Отправлен -> Доставлен).*

## 4. Связи в UML (Кратко)
*   **Зависимость** (пунктирная стрелка) — слабая связь, изменение одного влияет на другого.
*   **Ассоциация** (линия) — объекты знают друг о друге.
*   **Обобщение** (стрелка с треугольником) — наследование.
*   **Реализация** (пунктир с треугольником) — реализация интерфейса.

## 5. Инструменты для создания UML
*   **Visual Studio** (встроенный конструктор классов и диаграмм).
*   **PlantUML** — создание диаграмм через код (текстом).
*   **draw.io / diagrams.net** — бесплатный онлайн-редактор.
*   **Lucidchart** — профессиональный веб-инструмент.
*   **StarUML** — десктопная программа.

## 6. Принципы хорошей UML-диаграммы
1.  **Не перегружайте:** не показывайте все классы проекта, только ключевые.
2.  **Соблюдайте нотацию:** используйте правильные стрелки и ромбы.
3.  **Уровень детализации:** диаграмма должна быть понятна целевой аудитории (для бизнеса — Use Case, для разработчиков — Class).
4.  **Именование:** имена классов и методов должны быть понятными (не `Class1`, `Method2`).

## 7. Пример: Как связаны диаграммы в проекте
1.  **Use Case** — определяем, *что* нужно пользователю.
2.  **Class Diagram** — проектируем *структуру* кода (какие классы создадим).
3.  **Sequence Diagram** — продумываем *логику* взаимодействия (как методы вызывают друг друга).
4.  **State Diagram** — описываем *поведение* сложных объектов (например, статус заказа).

## Глава 1. Организация процесса конструирования ПО

### 1.1. Определение технологии конструирования ПО

**Технология конструирования ПО (ТКПО)** — система инженерных принципов для создания экономичного ПО, которое надёжно и эффективно работает в реальных компьютерах.

Составляющие ТКПО:

| Компонент | Назначение |
|---|---|
| **Методы** | Планирование, анализ требований, проектирование, кодирование, тестирование, сопровождение |
| **Средства (утилиты)** | Автоматизированная поддержка методов; объединяются в CASE-системы (*Computer Aided Software Engineering*) |
| **Процедуры** | «Клей», соединяющий методы и утилиты в непрерывную технологическую цепочку; определяют формирование отчётов и «вех» |

**Парадигмы ТКПО** — последовательности шагов, использующие методы, утилиты и процедуры. Они вносят в процесс создания ПО организующее инженерное начало.

---

### 1.2. Классический жизненный цикл (водопадная модель)

**Автор:** Уинстон Ройс, 1970. Также называется **каскадной** или **водопадной** моделью.

**Суть:** разработка — последовательность этапов; переход на следующий этап происходит только после полного завершения работ на текущем.

**Этапы:**

1. **Системный анализ** — определение роли каждого элемента компьютерной системы, взаимодействия элементов; формирование требований ко всем системным элементам и выделение подмножества требований для ПО; начало планирования проекта.
2. **Анализ требований** — уточнение и детализация функций, характеристик и интерфейса ПО; документирование в спецификации анализа; завершение планирования проекта.
3. **Проектирование** — создание представлений:
   - архитектуры ПО;
   - модульной структуры;
   - алгоритмической структуры;
   - структуры данных;
   - входного и выходного интерфейса.
4. **Кодирование** — перевод результатов проектирования в текст на языке программирования.
5. **Тестирование** — выполнение программы для выявления дефектов в функциях, логике и форме реализации.
6. **Сопровождение** — внесение изменений в эксплуатируемое ПО:
   - исправление ошибок;
   - адаптация к изменениям внешней среды;
   - усовершенствование по требованиям заказчика.

> Сопровождение — повторное применение предшествующих этапов к существующей программе, а не разработка новой.

**Достоинства:**
- даёт план и временной график по всем этапам;
- упорядочивает ход конструирования.

**Недостатки:**
1. Реальные проекты часто требуют отклонения от стандартной последовательности шагов.
2. Цикл основан на точной формулировке исходных требований (реально в начале проекта требования определены лишь частично).
3. Результаты проекта доступны заказчику только в конце работы.

---

### 1.3. Макетирование (прототипирование)

**Причина применения:** заказчик не может сформулировать подробные требования, либо разработчик сомневается в приспособляемости продукта.

**Цель:** снять неопределённости в требованиях заказчика.

**Макетирование** — процесс создания модели требуемого программного продукта.

**Формы макета:**
1. бумажный макет или макет на основе ПК (изображает человеко-машинный диалог);
2. работающий макет (выполняет часть требуемых функций);
3. существующая программа (характеристики которой затем улучшаются).

**Последовательность действий:**
1. Сбор и уточнение требований.
2. Быстрое проектирование (внимание — на видимых пользователю характеристиках).
3. Построение макета.
4. Оценка макета заказчиком и уточнение требований.
5. Повторение итераций, пока макет не выявит все требования.

**Достоинство:** обеспечивает определение полных требований к ПО.

**Недостатки:**
- заказчик может принять макет за продукт;
- разработчик может принять макет за продукт (компромиссы по языку, ОС, алгоритмам «застревают» в системе).

---

### 1.4. Стратегии конструирования ПО

| Стратегия | В начале определены все требования? | Множество циклов конструирования? | Промежуточное ПО распространяется? |
|---|---|---|---|
| **Однократный проход** (водопадная) | Да | Нет | Нет |
| **Инкрементная** (запланированное улучшение продукта) | Да | Да | Может быть |
| **Эволюционная** | Нет | Да | Да |

- **Однократный проход** — линейная последовательность этапов.
- **Инкрементная** — все требования определены в начале, но реализация идёт последовательностью версий.
- **Эволюционная** — требования уточняются в результате разработки версий.

---

### 1.5. Инкрементная модель

Классический пример **инкрементной стратегии**. Объединяет элементы водопадной модели с итерационной философией макетирования.

**Суть:** каждая линейная последовательность (анализ → проектирование → кодирование → тестирование) вырабатывает поставляемый **инкремент** ПО.

- 1-й инкремент → базовый продукт (базовые требования).
- Каждый следующий инкремент → модификация базового продукта с дополнительной функциональностью.
- По своей природе процесс итеративен, но, в отличие от макетирования, обеспечивает на каждом инкременте **работающий продукт**.

**Современная реализация инкрементного подхода** — экстремальное программирование (XP, Кент Бек, 1999), ориентированное на очень малые приращения функциональности.

---

### 1.6. Быстрая разработка приложений (RAD)

**RAD (Rapid Application Development)** — второй пример инкрементной стратегии. Обеспечивает экстремально короткий цикл разработки (60–90 дней) за счёт **компонентно-ориентированного конструирования**.

**Этапы:**
1. **Бизнес-моделирование** — моделируется информационный поток между бизнес-функциями.
2. **Моделирование данных** — информационный поток отображается в набор объектов данных; определяются свойства и отношения.
3. **Моделирование обработки** — определяются преобразования объектов данных для реализации бизнес-функций.
4. **Генерация приложения** — использование языков 4-го поколения и повторно используемых компонентов.
5. **Тестирование и объединение** — многие компоненты уже протестированы, что уменьшает время.

**Условие применимости:** каждая главная функция может быть завершена за 3 месяца; каждая функция адресуется отдельной группе разработчиков.

**Ограничения RAD:**
1. Для больших проектов требуются существенные людские ресурсы.
2. Применима только для приложений, декомпозируемых на отдельные модули, где производительность не критична.
3. Не применима в условиях высоких технических рисков (новая технология).

---

### 1.7. Спиральная модель

**Автор:** Барри Боэм, 1988. Классический пример **эволюционной стратегии**. Базируется на лучших свойствах классического жизненного цикла и макетирования + новый элемент — **анализ риска**.

**Четыре действия (квадранта спирали):**
1. **Планирование** — определение целей, вариантов и ограничений.
2. **Анализ риска** — анализ вариантов и распознавание/выбор риска.
3. **Конструирование** — разработка продукта следующего уровня.
4. **Оценивание** — оценка заказчиком текущих результатов.

**Суть:** с каждой итерацией (продвижением от центра к периферии) строятся всё более полные версии ПО. Если риск слишком велик — проект может быть остановлен («продолжать / не продолжать»).

**Достоинства:**
1. Наиболее реально (в виде эволюции) отображает разработку ПО.
2. Позволяет явно учитывать риск на каждом витке.
3. Включает шаг системного подхода в итерационную структуру.
4. Использует моделирование для уменьшения риска.

**Недостатки:**
1. Новизна (отсутствует достаточная статистика эффективности).
2. Повышенные требования к заказчику.
3. Трудности контроля и управления временем разработки.

---

### 1.8. Компонентно-ориентированная модель

Развитие спиральной модели; тоже основывается на **эволюционной стратегии**. Конкретизирует содержание квадранта конструирования: новая разработка должна основываться на **повторном использовании существующих программных компонентов**.

**Схема работы:**
1. Компоненты, созданные в реализованных проектах, хранятся в **библиотеке**.
2. В новом проекте по требованиям заказчика выявляются **кандидаты в компоненты**.
3. Проверяется наличие кандидатов в библиотеке.
4. Если найдены — извлекаются и используются повторно.
5. Иначе — создаются новые компоненты, применяются и включаются в библиотеку.

**Достоинства:**
1. Уменьшает на 30% время разработки.
2. Уменьшает стоимость разработки до 70%.
3. Увеличивает в полтора раза производительность разработки.

---

### 1.9. Тяжеловесные и облегчённые (подвижные) процессы

Два семейства процессов разработки:

| Семейство | Характеристика | Область применения |
|---|---|---|
| **Прогнозирующие (тяжеловесные, heavyweight)** | Прогнозируется весь объём работ; строгий порядок; большой объём документации; человеческие слабости не учитываются | Фиксированные требования; многочисленная группа разработчиков разной квалификации |
| **Адаптивные (подвижные, облегчённые, lightweight/agile)** | Меньший объём документации; ориентированы на человека; адаптируются к частым изменениям требований | Частые изменения требований; малочисленная группа высококвалифицированных разработчиков; грамотный заказчик, участвующий в разработке |

> Для прогнозирующих процессов частые изменения требований «подобны смерти». Подвижные процессы адаптируются к изменениям и даже выигрывают от них.

---

### 1.10. XP-процесс (экстремальное программирование)

**Автор:** Кент Бек, 1999. Облегчённый (подвижный) процесс. Ориентирован на группы малого и среднего размера (до 10 сотрудников в одном помещении) при неопределённых или быстро изменяющихся требованиях.

**Основная идея:** устранить высокую стоимость изменения, характерную для приложений с объектами, паттернами и реляционными БД.

**Четыре базовых действия в XP-цикле:** кодирование, тестирование, выслушивание заказчика, проектирование.

**Четыре характеристики динамизма:**
- непрерывная связь с заказчиком;
- простота (всегда выбирается минимальное решение);
- быстрая обратная связь (модульное и функциональное тестирование);
- смелость в проведении профилактики проблем.

**Двенадцать методов XP:**
1. **Игра планирования** (Planning game) — быстрое определение области следующей реализации через объединение деловых приоритетов и технических оценок.
2. **Частая смена версий** (Small releases) — быстрый запуск простой системы; новые версии в двухнедельном цикле.
3. **Метафора** (Metaphor) — разработка на основе простой общедоступной истории о работе системы.
4. **Простое проектирование** (Simple design) — настолько просто, насколько возможно сейчас.
5. **Тестирование** (Testing) — непрерывное написание тестов; «тестируй, а затем кодируй».
6. **Реорганизация** (Refactoring) — реструктуризация без изменения поведения; устранение дублирования, улучшение взаимодействия.
7. **Парное программирование** (Pair programming) — весь код пишется двумя программистами за одним компьютером.
8. **Коллективное владение кодом** (Collective ownership) — любой разработчик может улучшать любой код в любое время.
9. **Непрерывная интеграция** (Continuous integration) — система интегрируется и строится много раз в день.
10. **40-часовая неделя** (40-hour week) — нельзя удваивать рабочую неделю за счёт сверхурочных.
11. **Локальный заказчик** (On-site customer) — представитель заказчика всё время в группе.
12. **Стандарты кодирования** (Coding standards) — единое представление кода во всех частях системы.

**Структура «идеального» XP-процесса:**
- Основной элемент — **XP-реализация**, в которую многократно вкладывается **XP-итерация**.
- Три фазы: **исследование** (поиск новых требований/историй), **блокировка** (выбор подмножества для реализации), **регулирование** (проведение разработки).
- Первая реализация: 2–6 месяцев; остальные — около 2 месяцев; итерация ~2 недели; группа ≤ 10 человек.

**Ключевые метрики:** «скорость проекта» — количество историй заданного размера, реализуемых в итерации.

---

### 1.11. Модели качества процессов (CMM)

Для гарантии качества процесса используется сертификат соответствия международным стандартам. Наиболее авторитетные модели:
- **ISO 9001:2000** — ориентирована на процессы разработки из любых областей.
- **ISO/IEC 15504** — специализируется на процессах программной разработки, более детализирован (объём > 500 страниц).
- **CMM** (Capability Maturity Model) Института программной инженерии при университете Карнеги-Меллон.

**Базовое понятие CMM — зрелость компании:**
- **Незрелая компания** — процесс и решения зависят только от таланта конкретных разработчиков; высока вероятность превышения бюджета и срывов сроков.
- **Зрелая компания** — ясные процедуры управления проектами и построения продуктов; точные оценки; корпоративные стандарты.

**Пять уровней зрелости CMM:**

| Уровень | Название | Характеристика |
|---|---|---|
| 1 | **Начальный** | Процесс не формализован, успех случаен, зависит от личных качеств сотрудников |
| 2 | **Повторяемый** | Внедрены формальные процедуры для основных элементов; процесс планируется и контролируется |
| 3 | **Определённый** | Все элементы процесса определены, стандартизированы и задокументированы на основе единого стандарта компании |
| 4 | **Управляемый** | Принимаются количественные показатели качества продуктов и процесса; более объективная оценка |
| 5 | **Оптимизирующий** | Постоянное улучшение и повышение эффективности процессов, ввод новых технологий |

Каждый уровень характеризуется **областью ключевых процессов (ОКП)**; следующий уровень включает все характеристики предыдущих. Если хотя бы одна цель ОКП не достигнута — компания не соответствует уровню.

## Глава 2. Руководство программным проектом

### 2.1. Процесс руководства проектом

**Руководство программным проектом** — первый «слой» процесса конструирования ПО; определяет сущность процесса разработки от начала до конца. Обеспечивает понимание:
- объёма предстоящих работ;
- возможного риска;
- требуемых ресурсов;
- предстоящих задач;
- вех;
- необходимых усилий (стоимости);
- плана работ.

**Перед планированием проекта следует:**
- установить цели и проблемную область проекта;
- обсудить альтернативные решения;
- выявить технические и управленческие ограничения.

**Основные стадии:**
1. **Начало проекта** — цели, альтернативы, ограничения.
2. **Измерения** — процесс и продукт.
3. **Оценка** — людские ресурсы (человеко-месяцы), длительность, стоимость.
4. **Анализ риска** — область неопределённости, решение «выполнять / не выполнять».
5. **Планирование** — набор задач, связи, сложность, ресурсы, сетевой график.
6. **Трассировка и контроль** — отслеживание задач, повторное планирование.

> **Веха** — временная метка, к которой привязано подведение промежуточных итогов. Вехи должны быть расставлены через регулярные интервалы.

---

### 2.2. Измерения, меры и метрики

- **Измерения** помогают понять как процесс разработки, так и сам продукт.
- **Мера** — количественная характеристика какого-либо свойства объекта.
- **Метрика** — вычисляемая функция от опорных характеристик, дающая числовое значение.

> В IEEE Standard Glossary of Software Engineering Terms: **метрика** — мера степени обладания свойством, имеющая числовое значение. В программной инженерии понятия «мера» и «метрика» часто рассматриваются как синонимы.

---

### 2.3. Планирование проектных задач (WBS)

**WBS (Work Breakdown Structure)** — структура распределения работ. Составляется с помощью утилиты планирования.

**Типовые первые задачи:** системный анализ и анализ требований.

**Системный анализ проводится с целью:**
1. выяснения потребностей заказчика;
2. оценки выполнимости системы;
3. экономического и технического анализа;
4. распределения функций по элементам компьютерной системы;
5. определения стоимости и ограничений планирования;
6. создания системной спецификации.

**Анализ требований даёт возможность:**
1. определить функции и характеристики продукта;
2. обозначить интерфейс с другими системными элементами;
3. определить проектные ограничения;
4. построить модели процесса, данных, режимов функционирования;
5. создать формы представления информации и функций для проектирования.

**Параллельность:** задачи проектирования и планирования тестов могут быть распараллелены; для каждого модуля — параллельный путь детального проектирования, кодирования и тестирования.

**Оценки времени выполнения задачи:**
- $T_{min}^{in}$ — раннее время начала;
- $T_{max}^{in}$ — позднее время начала;
- $T_{min}^{out} = T_{min}^{in} + T_{resh}$ — раннее время конца;
- $T_{max}^{out} = T_{max}^{in} + T_{resh}$ — позднее время конца;
- **общий резерв** — количество избытков/потерь планирования, не приводящих к увеличению длительности критического пути $T_{к.п.}$.

**Рекомендуемое правило распределения затрат проекта — 40-20-40:**
- 40% — анализ и проектирование (из них 5% — планирование и системный анализ);
- 20% — кодирование;
- 40% — тестирование и отладка.

---

### 2.4. Размерно-ориентированные метрики (LOC)

Прямо измеряют программный продукт и процесс. Основаны на **LOC-оценках** (Lines Of Code).

**Исходные данные (пример):**

| Проект | Затраты, чел.-мес | Стоимость, тыс. $ | KLOC | Документы, стр. | Ошибки | Люди |
|---|---|---|---|---|---|---|
| aaa01 | 24 | 168 | 12,1 | 365 | 29 | 3 |
| bbb02 | 62 | 440 | 27,2 | 1224 | 86 | 5 |
| ccc03 | 43 | 314 | 20,2 | 1050 | 64 | 6 |

**Метрики (для каждого проекта):**

$$\text{Производительность} = \frac{\text{Длина}}{\text{Затраты}} \left[ \frac{\text{тыс. LOC}}{\text{чел.-мес}} \right]$$

$$\text{Качество} = \frac{\text{Ошибки}}{\text{Длина}} \left[ \frac{\text{единиц}}{\text{тыс. LOC}} \right]$$

$$\text{Удельная стоимость} = \frac{\text{Стоимость}}{\text{Длина}} \left[ \frac{\text{тыс.}}{\text{LOC}} \right]$$

$$\text{Документированность} = \frac{\text{Страниц документа}}{\text{Длина}} \left[ \frac{\text{страниц}}{\text{тыс. LOC}} \right]$$

**Достоинства:** широко распространены; просты и легко вычисляются.

**Недостатки:**
1. Зависимость от языка программирования.
2. Требуют исходных данных, которые трудно получить на начальной стадии.
3. Не приспособлены к непроцедурным языкам.

---

### 2.5. Функционально-ориентированные метрики (FP)

Косвенно измеряют продукт и процесс; рассматривают **функциональность** или **полезность** продукта.

**Пять информационных характеристик:**
1. Количество **внешних вводов** — вводы пользователя с разными прикладными данными (отделены от запросов).
2. Количество **внешних выводов** — отчёты, экраны, распечатки, сообщения об ошибках.
3. Количество **внешних запросов** — диалоговый ввод, приводящий к немедленному диалоговому выводу (без сохранения ввода и без вычислений).
4. Количество **внутренних логических файлов** — логические группы данных внутри приложения.
5. Количество **внешних интерфейсных файлов** — логические файлы из других приложений, на которые ссылается данное.

**Транзакция** — элементарный процесс, различаемый пользователем и перемещающий данные между внешней средой и приложением.

**Ранжирование и оценка сложности** — по таблицам (низкий/средний/высокий ранг; числовая оценка). Для транзакций — по количеству ссылок на файлы и количеству типов элементов данных; для файлов — по количеству типов элементов-записей и типов элементов данных.

**Расчёт:**

$$FP = \text{Общее количество} \times \left(0{,}65 + 0{,}01 \times \sum_{i=1}^{14} F_i\right)$$

где $F_i$ — коэффициенты регулировки сложности (0 — нет влияния, 1 — случайное, 2 — небольшое, 3 — среднее, 4 — важное, 5 — основное), выбираемые по 14 системным параметрам (передачи данных, распределённая обработка, производительность, распространённость конфигурации, скорость транзакций, оперативный ввод, эффективность конечного пользователя, оперативное обновление, сложность обработки, повторная используемость, лёгкость инсталляции, лёгкость эксплуатации, разнообразные условия размещения, простота изменений).

**Метрики на основе FP:**

$$\text{Производительность} = \frac{\text{ФункцУказатель}}{\text{Затраты}} \left[ \frac{\text{FP}}{\text{чел.-мес}} \right]$$

$$\text{Качество} = \frac{\text{Ошибки}}{\text{ФункцУказатель}} \left[ \frac{\text{единиц}}{\text{FP}} \right]$$

$$\text{Удельная стоимость} = \frac{\text{Стоимость}}{\text{ФункцУказатель}} \left[ \frac{\text{тыс.}}{\text{FP}} \right]$$

$$\text{Документированность} = \frac{\text{Страниц документа}}{\text{ФункцУказатель}} \left[ \frac{\text{страниц}}{\text{FP}} \right]$$

**Указатели свойств (Features Points)** — для систем с высокой алгоритмической сложностью (системное, инженерное ПО, ПО реального времени, встроенное ПО). Добавляется характеристика **количество алгоритмов** (например, обработка прерываний, инвертирование матрицы, расшифровка битовой строки).

**Пересчёт FP → LOC** (зависит от языка): Ассемблер — 320, C — 128, Кобол/Фортран — 106, Паскаль — 90, C++ — 64, Java — 53, Ada 95 — 49, Visual Basic — 32, Delphi Pascal — 29, Smalltalk — 22, Perl — 21, HTML3 — 15 и т. д.

**Достоинства FP-метрик:**
1. Не зависят от языка программирования.
2. Легко вычисляются на любой стадии проекта.

**Недостаток:** результаты основаны на субъективных данных; используются косвенные измерения.

### 2.6. Процесс оценки проекта

**Цель:** сформировать предварительные оценки, позволяющие предъявить заказчику корректные требования по стоимости и затратам и составить план проекта.

**Шаги оценки:**

1. **Разбиение области назначения** на функции $f_1, f_2, \dots, f_n$.
2. **Для каждой функции** — лучшая, худшая и вероятная оценка LOC (FP).
3. **Ожидаемое значение** по β-распределению:
   $$\text{LOC}_{\text{ож}} = \frac{\text{LOC}_{\text{лучш}} + \text{LOC}_{\text{худш}} + 4 \times \text{LOC}_{\text{вероятн}}}{6}$$
4. **Производительность разработки функции** — один из трёх подходов:
   - средняя производительность $$\text{ПРОИЗВ}_{ср}$$ для всех функций (минимальная точность, максимальная простота);
   - настраиваемая: $$\text{ПРОИЗВ}_i = \text{ПРОИЗВ}_{ср} \times (\text{LOC}_{ср} / \text{LOC}_{\text{ож}i})$$;
   - по аналогу: $$\text{ПРОИЗВ}_i = \text{ПРОИЗВ}_{ан} \times (\text{LOC}_{ан} / \text{LOC}_{\text{ож}i})$$ (максимальная точность, максимальная сложность).
5. **Общая оценка затрат:**
   - для первого подхода: $$\text{ЗАТРАТЫ} = \left(\sum \text{LOC}_{\text{ож}i}\right) / \text{ПРОИЗВ}_{ср}$$;
   - для второго и третьего: $$\text{ЗАТРАТЫ} = \sum (\text{LOC}_{\text{ож}i} / \text{ПРОИЗВ}_i)$$.
6. **Общая оценка стоимости:**
   - для первого и второго: $$\text{СТОИМОСТЬ} = \left(\sum \text{LOC}_{\text{ож}i}\right) \times \text{УД\_СТОИМОСТЬ}_{ср}$$;
   - для третьего: $$\text{СТОИМОСТЬ} = \sum (\text{LOC}_{\text{ож}i} \times \text{УД\_СТОИМОСТЬ}_{анi})$$.

**Пример (фрагмент):** для 7 функций ПО рабочей станции дизайнера автомобиля получены итоговые оценки: LOC ≈ 33 360, стоимость ≈ $656 680, затраты ≈ 146 чел.-мес. Проверка через FP-указатели дала 372 FP, затраты ≈ 145,9 чел.-мес, стоимость ≈ $656 500; проверка через COCOMO II — 145,87 чел.-мес. Результаты совпали с хорошей достоверностью.

### 2.7. Конструктивная модель стоимости COCOMO

**Автор:** Барри Боэм, 1981 (COCOMO 81). Статистический подход — учитывались реальные результаты огромного количества проектов.

**Три подмодели COCOMO 81:**
- **Базисная** — статическая модель; затраты как функция размера программы.
- **Промежуточная** — дополнительно учитывает атрибуты стоимости (оценки продукта, аппаратуры, персонала, проектной среды).
- **Усовершенствованная** — учитывает влияние всех атрибутов стоимости на каждый этап процесса разработки.

**Три типа проектов:**
- **Распространённый** — небольшие проекты, небольшая группа с хорошим стажем, мягкие требования.
- **Полунезависимый** — средний проект, группа с разным опытом, мягкие и жёсткие требования.
- **Встроенный** — жёсткие аппаратные, программные и вычислительные ограничения.

**Уравнения базовой подмодели:**
$$E = a_b \times (KLOC)^{b_b} \quad [\text{чел.-мес}]$$
$$D = c_b \times (E)^{d_b} \quad [\text{мес}]$$

**Коэффициенты базовой подмодели:**

| Тип проекта | $a_b$ | $b_b$ | $c_b$ | $d_b$ |
|---|---|---|---|---|
| Распространённый | 2,4 | 1,05 | 2,5 | 0,38 |
| Полунезависимый | 3,0 | 1,12 | 2,5 | 0,35 |
| Встроенный | 3,6 | 1,20 | 2,5 | 0,32 |

#### COCOMO II (1995)

Ориентирована на программную инженерию XXI века. В состав входят:
- **модель композиции приложения**;
- **модель раннего этапа проектирования**;
- **модель этапа пост-архитектуры**.

Для описания моделей требуется информация о размере продукта: LOC-оценки, объектные указатели, функциональные указатели.

**Модель композиции приложения** — на ранней стадии (макетирование интерфейсов, взаимодействие ПО и системы, оценка производительности, степень зрелости технологии). Ориентирована на **объектные указатели** (количество экранов, отчётов, компонентов).

$$NOP = (\text{Объектные указатели}) \times \frac{100 - \%REUSE}{100}$$

$$\text{ЗАТРАТЫ} = NOP / PROD \quad [\text{чел.-мес}]$$

где $PROD$ — скорость разработки (от 4 при очень низкой опытности и зрелости среды до 50 при очень высокой).

**Модель раннего этапа проектирования** (стабилизация требований и базисной архитектуры):

$$\text{ЗАТРАТЫ} = A \times РАЗМЕР^B \times M_e + \text{ЗАТРАТЫ}_{auto} \quad [\text{чел.-мес}]$$

- $A = 2{,}5$;
- $B$ — показатель нелинейной зависимости затрат от размера, $B = 1{,}01 + 0{,}01 \sum_{i=1}^{5} W_i$ (диапазон 1,01…1,26);
- $M_e = \prod_{i=1}^{7} EM_i$ — множитель поправки по 7 формирователям затрат (PERS — возможности персонала, RCPX — надёжность и сложность продукта, RUSE — требуемое повторное использование, PDIF — трудность платформы, PREX — опытность персонала, FCIL — средства поддержки, SCED — график);
- $\text{ЗАТРАТЫ}_{auto} = (KALOC \times AT/100) / ATPROD$ — затраты на автоматически генерируемый код.

**Пять масштабных факторов $W_i$** (оценки от 5 — очень низкий до 0 — сверхвысокий):
- **PREC** — предсказуемость (предыдущий опыт);
- **FLEX** — гибкость разработки;
- **RESL** — разрешение архитектуры/риска (степень анализа риска);
- **TEAM** — связность группы;
- **PMAT** — зрелость процесса (по вопроснику CMM).

**Модель этапа пост-архитектуры** (когда архитектура сформирована):

$$\text{ЗАТРАТЫ} = A \times K_{req} \times РАЗМЕР^B \times M_p + \text{ЗАТРАТЫ}_{auto}$$

- $K_{req} = 1 + (BRAK/100)$ — учёт изменчивости требований (процент отброшенного/модифицированного кода);
- $РАЗМЕР = РАЗМЕР_{new} + РАЗМЕР_{reuse}$;
- $M_p = \prod_{i=1}^{17} EM_i$ — множитель поправки по 17 факторам затрат, сгруппированным по 4 категориям:
  - **продукт:** RELY (надёжность), DATA (размер БД), CPLX (сложность), RUSE (повторная используемость), DOCU (документирование жизненного цикла);
  - **платформа:** TIME (ограничения времени выполнения), STOR (ограничения памяти), PVOL (изменчивость платформы);
  - **персонал:** ACAP (возможности аналитика), PCAP (возможности программиста), AEXP (опыт с приложением), PEXP (опыт с платформой), LTEX (опыт с языком и утилитами), PCON (непрерывность персонала);
  - **проект:** TOOL (использование утилит), SITE (мультисетевая разработка), SCED (требуемый график).

> $M_p$ позволяет троекратно увеличить (уменьшить) начальную оценку затрат.

**Стоимость:**
$$\text{СТОИМОСТЬ} = \text{ЗАТРАТЫ} \times РАБ\_КОЭФ$$
(среднее значение рабочего коэффициента ≈ $15 000 за человеко-месяц).

**Длительность:**
$$TDEV = \left[3{,}0 \times (\text{ЗАТРАТЫ})^{(0{,}33 + 0{,}2(B - 1{,}01))}\right] \times \frac{SCEDPercentage}{100} \quad [\text{мес}]$$

> COCOMO II ограничивает диапазон уплотнения/растягивания графика (75–160%), иначе в проект вносится высокий риск.

**Важное следствие:** удвоение разработчиков не приводит к двукратному сокращению длительности. Причины:
- увеличивается время на взаимодействие и обучение;
- возрастает время на определение интерфейсов между частями системы.

> Количество людей, требуемых на этапах планирования и формирования требований, невелико; на проектировании и кодировании потребность возрастает; после кодирования и тестирования — достигает минимума.

## 6.1. Основные понятия и принципы тестирования

**Тестирование** — это процесс выполнения программы с целью обнаружения ошибок. Шаги процесса задаются тестами.

**Что такое тест?**
Тест (тестовый вариант) определяет:
- набор исходных данных и условий для запуска программы;
- набор ожидаемых результатов работы программы.

**Что может и чего не может тестирование:**
- **Может:** обнаружить ошибки, продемонстрировать соответствие функций назначению, показать надёжность.
- **Не может:** доказать отсутствие дефектов. Тестирование может показать только *присутствие* ошибок, но никогда не гарантирует их полное отсутствие.

**Исчерпывающее тестирование** — проверка всех возможных наборов данных. На практике невозможно из-за огромных временных затрат.

**Цель проектирования тестов** — систематическое обнаружение различных классов ошибок при минимальных затратах времени и стоимости.

---

## 6.2. Два подхода к тестированию (Принципы)

Существует два основных принципа тестирования.

### «Чёрный ящик» (Функциональное тестирование)

- **Что известно:** функции программы.
- **Что исследуется:** работа каждой функции на всей области определения (входы и выходы).
- **Суть:** программа рассматривается как непрозрачный ящик. Мы не смотрим на код, а смотрим на результаты.
- **Недостаток:** не реагирует на многие особенности программных ошибок (например, ошибки в скрытых ветках логики).

### «Белый ящик» (Структурное тестирование)

- **Что известно:** внутренняя структура программы (исходный код).
- **Что исследуется:** внутренние элементы и связи между ними (управляющие связи, логика).
- **Суть:** проверяем корректность построения *всех* элементов программы и их взаимодействия.
- **Особенность:** программа считается полностью проверенной, если проведено исчерпывающее тестирование маршрутов (путей) её графа управления.

**Достоинства «белого ящика»:**

1. Позволяет учесть специфику ошибок (например, в «центре» программы ошибок меньше, чем на «периферии»).
2. Позволяет найти ошибки, не зависящие от входных данных (ошибки внутренних состояний).
3. Позволяет найти типовые ошибки трансляции (синтаксис, семантика).

## 6.3. Тестирование базового пути (Метод МакКейба)

Это способ тестирования «белого ящика», который позволяет оценить сложность программы и определить необходимое количество тестов.

### Потоковый граф

Программа представляется в виде графа:

- **Узлы** (вершины) — линейные участки кода (операторы).
- **Дуги** — поток управления (переходы между операторами).
- **Предикатные узлы** — узлы с условиями (из них выходит две дуги: True и False).

### Цикломатическая сложность

Это метрика \(V(G)\), которая показывает **количество независимых путей** в программе (и, следовательно, минимальное количество тестов).

Вычисляется тремя способами:

1. **Количество регионов** (замкнутых областей) на графе.
2. **Формула Эйлера:** \(V(G) = E - N + 2\), где \(E\) — дуги, \(N\) — узлы.
3. **Количество предикатных узлов + 1.**

*Пример:* если \(V(G) = 4\), значит, в программе 4 независимых пути и нужно минимум 4 теста.

### Шаги способа базового пути

1. Построить потоковый граф по коду.
2. Вычислить цикломатическую сложность.
3. Определить **базовое множество** (независимые пути).
   - *Независимый путь* — путь, который вводит новую дугу (новый оператор).
4. Подготовить тестовые варианты для каждого пути.

## 6.4. Тестирование условий

Цель — проверить логические условия в программе. Ошибки здесь могут быть в булевых операторах, переменных, скобках или операторах отношений.

**Способы:**

1. **Тестирование ветвей:** проверяем, чтобы каждое составное условие принимало значения True и False.
2. **Тестирование области определения:** для выражения \(E1 < E2\) генерируем 3 теста: \(E1 < E2\), \(E1 = E2\), \(E1 > E2\).
3. **Тестирование ветвей и операторов отношений:** используется для обнаружения ошибок в условиях, где булевы переменные и операторы отношений встречаются только по одному разу.

**Важный момент:** для составного условия (например, `a & b`) создаётся «ограничивающее множество» тестов (в данном случае: `(false, true)`, `(true, false)`, `(true, true)`), чтобы проверить влияние каждого простого условия на общий результат.

---

## 6.5. Тестирование потоков данных (DU-тестирование)

Здесь анализируется не только управление, но и **жизнь данных** в программе.

- **DEF(i)** — определение переменной в узле \(i\) (присваивание).
- **USE(i)** — использование переменной в узле \(i\) (чтение).
- **DU-цепочка** — путь от определения переменной до её использования.

**Суть метода:** тесты должны покрыть все DU-цепочки программы (то есть проверить, что все данные передаются корректно от места создания до места использования).

**Шаги:**

1. Построить управляющий граф.
2. Построить информационный граф (связи по данным).
3. Сформировать DU-цепочки.
4. Найти пути, покрывающие эти цепочки.

**Достоинство:** простота автоматизации.

**Недостаток:** сложно выбрать минимальное количество эффективных тестов.

## 6.6. Тестирование циклов

Цикл — самая распространённая конструкция, и тестировать его нужно особенно тщательно.

**Типы циклов:** простые, вложенные, объединённые, неструктурированные.

### Простые циклы

Для проверки цикла с \(n\) повторений используют набор тестов:

1. Пропуск цикла (0 итераций).
2. Один проход (1 итерация).
3. Два прохода (2 итерации).
4. \(m\) проходов (\(m < n\)).
5. \(n - 1\), \(n\), \(n + 1\) проходов (граничные значения).

### Вложенные циклы

Тестируются по методике от внутреннего к внешнему:

1. Начать с самого внутреннего цикла. Для него применить тесты простого цикла, а параметры внешних циклов зафиксировать (поставить минимальные значения).
2. Перейти к следующему (объемлющему) циклу. Зафиксировать минимальные значения для внешних циклов и **типовые (рабочие)** значения для уже проверенных внутренних.
3. Повторять, пока не проверим все циклы.

### Объединенные циклы

Если циклы независимы — тестируем как простые.
Если зависимы (например, счётчик первого — начало второго) — тестируем как вложенные.

### Неструктурированные циклы

**Тестированию не подлежат.** Их нужно переписать с использованием структурированных конструкций.

## Итог для пересказа (шпаргалка)

1. **Тестирование** — это поиск ошибок. Оно не доказывает их отсутствие.
2. **«Белый ящик»** смотрит внутрь кода. **«Чёрный ящик»** — только на вход и выход.
3. **Метод базового пути (МакКейб):** строим граф, считаем цикломатическую сложность (число независимых путей), пишем тесты для каждого пути.
4. **Тестирование условий:** проверяем логические выражения (True/False, граничные значения).
5. **Тестирование потоков данных (DU):** следим, чтобы данные доходили от места создания (DEF) до места использования (USE) без ошибок.
6. **Тестирование циклов:** проверяем 0, 1, 2, \(n-1\), \(n\), \(n+1\) итераций. Вложенные циклы идут от внутреннего к внешнему.
